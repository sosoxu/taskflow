## 1. 服务简介

TaskFlow 是一个基于 **C++17 + Vue 3** 构建的分布式任务调度系统，通过 Web 界面可视化编排工作流，并将任务分发到多个执行节点上运行。主要功能包括：

**任务管理**

- 支持 Command（命令行）、Script（Shell 脚本）、SQL（数据库执行）三种任务类型
- 可配置超时、重试次数与重试间隔、资源标签、参数与环境变量；每次编辑自动生成新版本
- 支持创建 / 编辑 / 软删除 / 详情查看 / 分页搜索筛选

**工作流编排**

- 可视化 DAG 编辑器：拖拽任务节点、连线建立依赖关系，连线时实时检测循环依赖
- 支持节点级参数覆盖（timeout / max_retries / retry_interval）
- 调度策略：random（随机）、load_balance（负载均衡）、specified（指定 Worker）
- 支持标准 5 字段 Cron 表达式定时触发

**执行与调度**

- DAG 引擎按拓扑排序驱动执行，上游失败自动将下游标记为 `UPSTREAM_FAILED`
- Scheduler 通过 gRPC 派发任务，支持资源标签匹配执行节点
- 执行控制：暂停 / 恢复 / 取消 / 任务级重试 / 任务级终止（kill）
- 超时自动检测、失败任务按配置自动重试

**高可用与扩展**

- Scheduler 支持多实例部署，基于 PostgreSQL Advisory Lock 自动选主，主节点故障后约 10 秒内接管
- Worker 支持动态注册与扩容：新增节点自动上线，停止后约 30 秒内被标记离线

**安全与可观测性**

- JWT 认证（accessToken + refreshToken）+ 登出黑名单
- RBAC 三级角色：admin（全部权限）、operator（读写）、viewer（只读）；非 admin 只能操作自己创建的资源
- 密码 bcrypt 加密；SQL 任务数据库密码 AES-256 加密存储；gRPC 可选双向 TLS
- 仪表盘统计、实例 DAG 按节点状态着色、基于 SSE 的任务日志实时跟踪、日志自动轮转与保留清理

## 2. 镜像清单与系统架构

`taskflow-images.tar` 为 `docker save` 产物，共包含 3 个镜像：

| 镜像 | 组件 | 对外端口 | 镜像内关键路径 |
|------|------|----------|----------------|
| `taskflow-scheduler:latest` | 调度器（REST API + DAG 引擎 + Cron + 任务分发 + 选主） | 8080（HTTP）、50051（gRPC） | 程序 `/app/scheduler`、配置 `/app/scheduler.yaml`、SQL `/app/sql/`、日志 `/app/logs/` |
| `taskflow-worker:latest` | 执行节点（接收并执行任务、上报状态与心跳） | 50052（gRPC） | 程序 `/app/worker`、配置 `/app/worker.yaml`、任务日志 `/app/logs/tasks/` |
| `taskflow-frontend:latest` | Web UI（Nginx 托管静态资源并反向代理 `/api/`） | 80 | 静态页面 `/usr/share/nginx/html` |

> 注意：镜像包不包含 PostgreSQL。容器编排中的 `postgres:16-alpine` 需要在目标机器上可拉取，或提前用 `docker load`/私有仓库导入。

系统整体架构：

```text
┌─────────────┐   REST/JSON    ┌──────────────────┐   gRPC/Protobuf   ┌─────────────────┐
│  前端容器    │ ◄────────────► │  调度器容器        │ ◄───────────────► │  Worker 容器(可多个)│
│  Nginx:80   │                │  HTTP:8080        │                   │  gRPC:50052      │
└─────────────┘                │  gRPC:50051       │                   └─────────────────┘
                               └─────────┬────────┘
                                         │ libpqxx
                              ┌──────────▼──────────┐
                              │ PostgreSQL 15+       │
                              │ （任务/工作流/用户/Cron 持久化）│
                              └─────────────────────┘
```

## 3. 环境要求

- Docker 20.10+，Docker Compose V2（支持 `docker compose` 命令）
- PostgreSQL 15+（推荐使用 `postgres:16-alpine` 容器）
- 主机空闲端口：`80`、`8080`（手动部署时可选 `50051`、`5432`）
- 磁盘空间：镜像加载约需 1 GB 以上

## 4. 加载镜像

在目标机器上执行：

```bash
docker load -i taskflow-images.tar
```

加载完成后确认镜像存在：

```bash
docker images | grep taskflow
```

应能看到：

```text
taskflow-frontend   latest   ...
taskflow-scheduler  latest   ...
taskflow-worker     latest   ...
```

镜像内默认配置为示例值（数据库密码、JWT 密钥等为空或需按环境修改），**不建议直接以默认配置运行生产环境**，请按第 5、6 节提供配置。

## 5. 部署方式一：Docker Compose 一键部署（推荐）

仓库根目录的 `docker-compose.yml` 已编排好 PostgreSQL、Scheduler、Worker、Frontend 四个服务，并在 PostgreSQL 首次启动时自动执行 `backend/sql/schema.sql` 初始化数据库。

### 5.1 启动服务

镜像已加载的情况下，使用 `--no-build` 可跳过源码构建，直接使用镜像：

```bash
cd taskflow
docker compose up -d --no-build
```

也可以使用仓库自带的 `./start.sh start`（镜像存在时不会重新构建，但离线环境中若缺少依赖基础镜像，`start.sh` 可能尝试联网构建，因此推荐上面的 `--no-build` 方式）。

> 离线部署注意：`postgres:16-alpine` 不在 `taskflow-images.tar` 中。若目标机器无该镜像且无法联网，请先单独导入数据库镜像，或修改 compose 使用本机已有的 PostgreSQL。

### 5.2 查看状态与日志

```bash
docker compose ps
docker compose logs -f scheduler   # 调度器日志
docker compose logs -f worker      # 执行节点日志
```

### 5.3 多 Worker 扩容

```bash
# 启动 3 个 Worker 实例
docker compose up -d --no-build --scale worker=3
```

Worker 支持动态增减，扩容或缩容无需重启 Scheduler。

### 5.4 停止服务

```bash
docker compose down          # 停止并删除容器（保留数据卷）
docker compose down -v       # 停止并删除容器和数据卷（数据不可恢复，慎用）
```

## 6. 部署方式二：手动 docker run

此方式不依赖 Compose，适合需要理解每个镜像如何连接、或想精细控制容器参数的场景。以下所有容器需加入同一个 Docker 网络，前端 Nginx 通过主机名 `scheduler` 访问调度器 API。

以下命令默认在仓库根目录（含 `backend/sql/schema.sql` 的目录）执行。

### 6.1 创建网络

```bash
docker network create taskflow-net
```

### 6.2 启动 PostgreSQL 并初始化数据库

```bash
docker run -d --name taskflow-postgres --network taskflow-net \
  -e POSTGRES_DB=taskflow \
  -e POSTGRES_USER=taskflow \
  -e POSTGRES_PASSWORD=taskflow123 \
  -v taskflow-pgdata:/var/lib/postgresql/data \
  -v "$PWD/backend/sql/schema.sql:/docker-entrypoint-initdb.d/01-schema.sql:ro" \
  -p 5432:5432 \
  postgres:16-alpine
```

`schema.sql` 会创建数据表并写入初始管理员账号（`admin` / `admin123`）。

### 6.3 准备配置文件

新建 `scheduler.yaml`（与仓库 `docker-compose.yml` 内嵌配置等价）：

```yaml
server:
  http_port: 8080
  grpc_port: 50051

database:
  host: taskflow-postgres     # 容器网络内的 PostgreSQL 主机名
  port: 5432
  name: taskflow
  user: taskflow
  password: "taskflow123"
  min_connections: 5
  max_connections: 20

auth:
  jwt_secret: "taskflow-jwt-secret-key-must-be-at-least-32-chars"   # >= 32 字符
  access_token_ttl: 86400
  refresh_token_ttl: 604800

encryption:
  aes_key: "taskflow-aes-key-must-be-32-characters"                 # 必须 32 字符

log:
  level: info
  file_path: logs/scheduler.log

schedule:
  dag_drive_interval: 2
  heartbeat_check_interval: 10
  heartbeat_timeout: 30
  timeout_check_interval: 10
  leader_lease_interval: 5
```

新建 `worker.yaml`：

```yaml
server:
  grpc_port: 50052
  # Docker 多 Worker 部署填 "auto"，让每个副本注册自己的容器 IP
  advertise_address: "auto"

scheduler:
  address: "scheduler:50051"   # Scheduler 容器的主机名和 gRPC 端口

worker:
  name: ""                     # 留空则自动生成
  max_tasks: 10                # 最大并发任务数
  resource_tags: []            # 资源标签，如 ["gpu", "high-mem"]

log:
  level: info
  file_path: logs/worker.log

task_log:
  dir: logs/tasks              # 任务日志目录
  retention_days: 30           # 日志保留天数
```

### 6.4 启动 Scheduler

```bash
docker run -d --name taskflow-scheduler --network taskflow-net \
  --network-alias scheduler \
  -p 8080:8080 -p 50051:50051 \
  -v "$PWD/scheduler.yaml:/app/scheduler.yaml:ro" \
  -v taskflow-scheduler-logs:/app/logs \
  taskflow-scheduler:latest
```

要点：

- `--network-alias scheduler` 必须保留：前端 Nginx 与 Worker 都通过主机名 `scheduler` 连接调度器
- 配置文件挂载到 `/app/scheduler.yaml`（镜像默认启动参数固定读取该路径）
- 若宿主机 8080 被占用，可改为 `-p 18080:8080`，前端访问不受影响（Nginx 在容器网络内部转发）

### 6.5 启动 Worker

```bash
docker run -d --name taskflow-worker --network taskflow-net \
  -v "$PWD/worker.yaml:/app/worker.yaml:ro" \
  -v taskflow-worker-logs:/app/logs \
  -v taskflow-worker-task-logs:/app/logs/tasks \
  taskflow-worker:latest
```

扩容 Worker：复制上面的命令并修改 `--name`（如 `taskflow-worker-2`、`taskflow-worker-3`）即可。每个 Worker 启动后会自动向 Scheduler 注册。

### 6.6 启动前端

```bash
docker run -d --name taskflow-frontend --network taskflow-net \
  -p 80:80 \
  taskflow-frontend:latest
```

若宿主机 80 端口被占用，可改为 `-p 18080:80`，然后通过 `http://localhost:18080` 访问。

## 7. 数据库初始化与升级

### 7.1 首次初始化

以上两种部署方式均在 PostgreSQL **首次启动（空数据卷）** 时自动执行建表脚本。若连接已有 PostgreSQL 实例，需手动初始化：

```bash
# 在已就绪的 PostgreSQL 上创建库、用户并建表
psql -h <db-host> -U <superuser> -c "CREATE USER taskflow WITH LOGIN PASSWORD 'taskflow123';"
psql -h <db-host> -U <superuser> -c "CREATE DATABASE taskflow OWNER taskflow;"
psql -h <db-host> -U taskflow -d taskflow -f backend/sql/schema.sql
```

仓库也提供了一键脚本（需以 `postgres` 系统用户执行）：

```bash
sudo -u postgres bash backend/sql/init_db.sh
```

### 7.2 版本升级

升级镜像版本后如需执行增量迁移，可在新库或已有库上执行：

```bash
psql -h <db-host> -U taskflow -d taskflow -f backend/sql/migrate_v1.sql
```

`backend/sql/schema.sql` 与迁移脚本同时存在于仓库和 Scheduler 镜像的 `/app/sql/` 目录中。

## 8. 访问与验证

部署完成后：

| 入口 | 地址 |
|------|------|
| Web 管理界面 | http://localhost |
| REST API | http://localhost:8080（健康检查 `/api/v1/health`） |
| Scheduler gRPC | localhost:50051 |
| PostgreSQL | localhost:5432（仅手动部署时对外暴露） |

验证服务健康：

```bash
curl http://localhost:8080/api/v1/health
# 期望返回: {"code":0,"message":"success","data":{"status":"ok"}}
```

浏览器打开 http://localhost，使用默认管理员登录：

| 用户名 | 密码 | 角色 |
|--------|------|------|
| admin | admin123 | admin |

> **重要**：首次登录后请立即修改默认密码，并按需修改 `jwt_secret`、`aes_key` 与数据库密码。

登录后可以在“仪表盘”看到在线 Worker 数；创建任务或工作流并触发运行后，可在实例详情页观察 DAG 节点状态并实时跟踪任务日志。

## 9. 镜像更新与数据备份

### 9.1 更新镜像

拿到新版本的 `taskflow-images.tar` 后：

```bash
docker load -i taskflow-images.tar
docker compose up -d --no-build        # 会以新镜像重建容器
docker image prune                     # 可选：清理旧镜像的悬空层
```

### 9.2 数据备份

业务数据（任务、工作流、实例、用户、Cron 配置）全部存储在 PostgreSQL 中，建议定期备份：

```bash
docker exec taskflow-postgres pg_dump -U taskflow -d taskflow > taskflow-backup-$(date +%F).sql
```

日志位于数据卷 `scheduler-logs`、`worker-logs`、`worker-task-logs`，删除容器不会删除数据卷，除非使用 `docker compose down -v` 或手动删除卷。

## 10. 常见问题

**Q1：Scheduler 启动后立即退出，日志提示“数据库连接池初始化失败”**

检查 `scheduler.yaml` 中 `database.host/port/user/password` 是否与 PostgreSQL 容器一致；确认 Scheduler 与 PostgreSQL 在同一 Docker 网络；PostgreSQL 未就绪时可稍等重试（compose 部署已通过 healthcheck 处理依赖顺序）。

**Q2：仪表盘中看不到 Worker**

查看 Worker 日志确认其已连接 Scheduler：

```bash
docker logs -f taskflow-worker
```

确认 `worker.yaml` 的 `scheduler.address` 可解析到 Scheduler 容器（手动部署时应为 `scheduler:50051`）；Docker 内多个 Worker 必须设置 `advertise_address: "auto"`，否则注册的地址不可达。

**Q3：前端页面能打开，但 API 请求报 502**

前端 Nginx 固定将 `/api/` 代理到 `http://scheduler:8080`。请确认前端与 Scheduler 在同一网络，且 Scheduler 容器的主机名为 `scheduler`（手动部署时使用 `--network-alias scheduler`）。

**Q4：登录提示账号或密码错误**

确认数据库已执行 `schema.sql`，并确认不是复用了旧数据卷导致初始化脚本被跳过；`docker compose down -v` 虽可清空数据卷重新初始化，但会丢失全部数据。

**Q5：宿主机端口被占用**

修改端口映射即可，例如 `-p 18080:80`、`-p 28080:8080`；容器内部端口无需修改。
